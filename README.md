# Full-stack template (FastAPI + React + Postgres)

A barebones, from-scratch full-stack starting point: FastAPI backend,
React + Vite + TypeScript frontend, Postgres via SQLModel/Alembic, a
Taskfile wrapping the whole workflow, dev + prod Docker setups, a
`.pre-commit-config.yaml`, and a Forgejo Actions CI workflow.

This repo is meant to be used as a **Forgejo template repository**
("Use this template" -> new repo), not cloned and worked on directly.

## Why there's a `setup.sh`

Nothing here pins tool versions in a way that goes stale. `pyproject.toml`
and the `package.json` files are checked in with their dependency lists
**empty** — `setup.sh` is what actually runs `uv add`,
`npm create vite@latest`, and `npm install -D @playwright/test@latest`,
so a repo created from this template starts on whatever's current the
day it's created, not whatever was latest when the template was last
edited.

`frontend/` itself doesn't exist in this repo — `setup.sh` scaffolds it
via `create-vite`, then copies `frontend-overlay/` on top (the
scaffold tool writes its own placeholder `App.tsx` etc., and the
overlay replaces those with the hello-world source).

## First use, after creating a repo from this template

`setup.sh` asks for a project name (used as `pyproject.toml`'s
`[project].name`) and then runs non-interactively from there:

    ./setup.sh
    git add -A
    git commit -m "Run setup.sh: resolve dependency versions"
    task hooks:install
    task dev

Then in another terminal, `task test`, `task test:frontend`, `task check`.
See `Taskfile.yml` (`task --list`) for everything else.

## What's checked in vs. what `setup.sh` generates

| Checked in (hand-written, doesn't go stale)                                   | Generated by `setup.sh`                                           |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `src/app/*`, `tests/*`, `scripts/*`                                            | `.venv/`, `uv.lock`, the dependency lists in `pyproject.toml`      |
| `alembic.ini`, `alembic/env.py`, `alembic/script.py.mako`                      | —                                                                   |
| `frontend-overlay/*`, `e2e/*`, root `playwright.config.ts`                     | `frontend/` (via `npm create vite@latest`), its `package-lock.json`|
| `Taskfile.yml`, `docker/`, `Dockerfile*`, `docker-compose*.yml`                | root/`e2e` `package-lock.json`, `node_modules/`                    |
| `.pre-commit-config.yaml`, `.forgejo/workflows/ci.yml`                         | —                                                                   |

`setup.sh` is safe to re-run for the backend and root/e2e npm installs
(it just re-resolves to current-latest); it skips the `frontend/`
scaffold step if that directory already exists, since re-running
`npm create vite@latest` there would prompt to overwrite.

## Forgejo CI

`.forgejo/workflows/ci.yml` is included but **no Forgejo runners are
registered on this cluster yet**, so it won't actually execute
anywhere until one is set up. It's there so CI is ready the moment a
runner exists — it hasn't been run for real. Once you do register a
runner, double check the `runs-on:` labels in that file match whatever
labels your runner advertises.

## Adding real models

`alembic/env.py` points `target_metadata` at `SQLModel.metadata`, but
no models are registered yet — this template ships zero tables on
purpose. Once you add a model module under `src/app/`, import it near
the top of `alembic/env.py` (see the commented-out line) so its table
shows up for `alembic revision --autogenerate`.
